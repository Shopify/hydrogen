`handleShopifyRoutes` now answers a Storefront API rate limit with HTTP `429`. This covers the built-in cart and predictive search routes, and any custom `createShopifyRouteHandler` handler that throws a `StorefrontApiError` with status `429`, also before the handler returns a promise. The response body is `{error: {code: "rate_limited", message}}` with a constant message, and the response has `Cache-Control: no-store` and a validated `Retry-After` header. A native form submission to the cart route gets the message as a plain-text `429` page instead, because the browser shows the response. The response never includes the upstream body. Before, the cart route returned `500` (`cart_mutation_failed`) or rejected, the predictive search route returned `400` with part of the upstream body in the message, and a custom handler's throw rejected the promise. The cart route, the predictive search route, and `handleShopifyRoutes` log the original error once at `error` level through Hydrogen's logger. The predictive search route now also logs its other failed Storefront API queries. `CartErrorCode` gains `"rate_limited"`, so an exhaustive `switch` on it needs a new case. A direct `cartHandlers.get()` call still throws the `StorefrontApiError`. Other Storefront API HTTP failures keep their previous handling, except that the predictive search error message no longer includes the upstream body.

A route handler's error result accepts `format: "text"` to send only its message as plain text. When a custom handler throws before it returns a promise, `handleShopifyRoutes` now returns a rejected promise, as its documentation describes. Before, the call itself threw.
