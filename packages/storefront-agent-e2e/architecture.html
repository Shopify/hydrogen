Spike · storefront-agent-e2e

Testing any storefront the way a shopper does

An AI agent shops a storefront using only what a person has: it sees screenshots and uses the mouse and keyboard. It never decides whether it succeeded. Shopify's own data does: the cart behind the checkout link, or the page the agent ended on.

Why not just scripted tests?

Scripted E2E (Playwright)

Encodes one storefront's markup: getByRole("button", { name: "Add to cart" }). Great for guaranteeing our templates' UX contract, but it can't follow a store with a cart page instead of a drawer, a newsletter popup, an age gate, a different language, or a country picker.

In the calibration runs, the scripted test failed two healthy stores (cart page only, newsletter popup), and the agent passed both.

Agent + state verifier

Describes the outcome ("add 2 of this variant, reach checkout") and lets the agent find its own route through whatever UI the store has. The verdict comes from Shopify's data, not from the page or the agent.

The question it answers: can a shopper actually complete this on this storefront?

Architecture

Purple is the only non-deterministic part. Everything that decides the verdict is green and deterministic.

Task generator deterministic

  • Reads the shop's catalog via the tokenless Storefront API
  • Detects the shop's default market (country, currency) and the storefront's language
  • Picks a target by seed: unique title, non-default variant, stock probed with a real cartCreate
  • Writes the goal in shopper language

Start page

  • The only navigation the harness does: home page or product page
→

Agent LLM

  • Stagehand v3 computer-use agent (open source), model swappable
  • Tools: screenshot, click, type, keys, scroll, wait, plus finish(done | blocked, reason, uxNotes)
  • No URL tool, no JavaScript, no DOM access
  • Prompt: act like a shopper, never type addresses, retry once then report blocked, respect loading states

Real Chrome

  • Real 1280×800 window; screenshots match the viewport
  • Native <select> lists drawn in-page so the agent can see them

Metering proxy

  • Passes model calls through, records tokens, cost and the agent's notes

Checkout capture deterministic

  • Chrome DevTools Protocol pauses the first document request to /cart/c/… or /checkouts/… (including redirect hops such as Shop Pay)
  • Records the URL and serves a "Checkout reached" stub: nothing irreversible happens
→

Verifier deterministic

  • Cart: cart id from the checkout URL → Storefront API cart(id) → exact variant and quantity
  • Product page: main heading equals the product title (or contains it with the handle in the URL)

Classifier deterministic

  • Agent claim × verified state → PASS / FAIL / BLOCKED / INCONCLUSIVE
  • Flags friction and collects UX notes

Outputs

  • run.json + journey report (filmstrip, clicks, reasoning, cost)
  • A plain Playwright replay script, when the run passes

Life of a run

A real run: Oh Polly, UK market, add-to-cart. 13 steps, 85 seconds, $0.35.

Generate the task.

The shop's default market is United Kingdom (GBP). The target is "Belted Cut-Out Mini Dress in Taupe", UK Size 10, stock-checked in the UK market. Goal: "Add 2 of … (UK Size: 10) to the cart, then go to checkout. Shop in the United Kingdom store (prices in GBP): if the store shows another country or currency, switch to United Kingdom."

Open the product page.

The harness's only navigation. From here on, only the agent acts.

The agent handles the store's own UI.

A geo popup says "United States". The agent opens the country dropdown, picks "UK + ROW", confirms, gets bounced once, and ends up on GBP prices.

It shops.

Selects UK Size 10, clicks Add to Bag. The drawer says "Your basket is empty" while a spinner is still running. The agent notes "it may still be loading", checks the cart icon (1 item), adds the second, then clicks Proceed to Checkout.

Checkout is captured.

The browser requests /checkouts/cn/<token>/en-us. The harness records it and shows a stub instead of the real checkout.

Shopify decides.

cart(id: "gid://shopify/Cart/<token>") returns 2 × Taupe dress, size 10. The target matches → PASS. The agent's notes show a correction → friction.

UX notes are reported.

"The cart briefly showed 'Your basket is empty' right after the first Add to Bag click, even though the item was actually added. This may alarm shoppers into double-adding items."

The two tests

T1 · Add a variant to cart

Start: product page, default variant selected.
Goal: add 2 of a non-default variant, reach checkout.
Verdict: the cart behind the checkout URL has exactly that variant × 2.

T2 · Find a product

Start: home page.
Goal: find the product page. Try search first, then collections or menus, then browse all products.
Verdict: the page the agent stops on has a main heading naming the product. The URL alone isn't enough: an error page at the right URL must fail.

Nothing in either test hardcodes a selector, button label, URL pattern or language. Product and option names come from Shopify in the storefront's language and market.

How the verdict is decided

The agent's claim never decides the outcome on its own. A store is only blamed when the agent finished or reported being stopped, and Shopify's state is wrong.

Agent claimState correctState wrong / no checkout
donePASSFAIL the UI lied, or the agent was fooled
blockedPASS the agent was confused, the store workedBLOCKED with the agent's diagnosis
gave up (steps or time ran out)PASSINCONCLUSIVE tells us nothing about the store
used a shortcut (typed a URL, browser keys)INCONCLUSIVE bypassed the storefront UI under test

friction is a PASS where the agent's own notes show it correcting or working around something ("only 1 item", "still shows", "try again"). The shopper could finish, but something was off, and that should be visible rather than hidden.

Guardrails

Block early

If the store contradicts an action, retry once, then finish("blocked"). No workarounds. Broken stores went from ~6 min and $2 per run to under 1 min and $0.15–0.38, with a precise diagnosis.

Exit interview

If steps or time run out, the agent is asked once (goal, its notes, last screenshot) whether the store stopped it. BLOCKED still requires that Shopify's state is wrong.

Step and time caps

20 steps, 10 minutes by default (configurable). A backstop: healthy runs take 4–13 steps.

Loading states

The agent checks for spinners, placeholders and disabled buttons before judging a result, and never re-adds to cart without checking it first.

Market and language

Keep the store's country, language and currency, unless the goal asks to switch to the run's market.

Cost metering

Every model call goes through a local proxy that records tokens, so each run reports its real cost.

The agent is a generation step, not a per-run cost

A passing agent run writes a plain, readable Playwright script. Day-to-day runs replay it with no AI. The agent only runs again when the script goes stale.

1 · Generate

  • Agent run passes
  • Clicks become role-based locators, e.g. getByRole("dialog", { name: "Cart" }).getByRole("link", { name: "Buy with Shop Pay" })

2 · Replay

  • No AI, $0, 2–9 seconds
  • Same verifier at the end

3 · Stale?

  • A recorded step stops working → stale → regenerate
  • Steps work but the cart is wrong (twice) → storefront FAIL, never regenerated

4 · Heal, visibly

  • Demo: a sale banner blocked the home script; the agent regenerated it with a "Close" step
  • The product script was untouched
  • The diff shows what changed

Calibration: does it tell healthy stores from broken ones?

We injected faults into our own React Router template (spike-only switches) and ran the agent against healthy and broken builds. 2 trials per row; the numbers show direction, not proof.

8/8

healthy runs PASS, including cart-page-only and popup variants the scripted test failed

8/8

hard faults (wrong variant added, add to cart broken) caught as BLOCKED with a diagnosis

4/4

"quantity ignored" runs: PASS with friction. The agent fixed the quantity in the cart, as a shopper could

$0.14–0.38

per agent run (healthy or broken). Replays: $0

Pre-registered thresholds: healthy false FAIL ≤ 2%, healthy BLOCKED + INCONCLUSIVE ≤ 10%, broken caught ≥ 95%. A full-size matrix (about 60 runs) is next.

Harness lessons

What the real stores taught the harness

• Screenshots must match the viewport (a hidden bottom strip made a checkout button "disappear").
• Native <select> lists are invisible to screenshots; we now draw them in-page.
• Agents are impatient; loading states need explicit attention.
• The URL alone can't prove you're on a product page.
