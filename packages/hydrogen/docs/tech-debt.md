# Tech Debt

Tracked items that are known shortcomings, deferred decisions, or missing guardrails. Each entry should describe what's missing, why it matters, and what "done" looks like.

## Local Shop Pay button does not emit shop-js impression analytics

**Status:** Open
**Added:** 2026-05-29

**What:** Hydrogen now renders the Shop Pay button locally instead of loading the hosted `shop-js` pay-button module. That removes the hosted custom element's `shop_js_ui_impression/1.1` path, including its reads from legacy Shopify analytics globals such as `window.ShopifyAnalytics`, `window.analytics`, or `window.trekkie`.

**Why it matters:** The local button has fewer runtime dependencies, but Shop Pay button impressions may remain missing or under-attributed unless Hydrogen publishes an equivalent event through its own analytics pipeline.

**Done when:** Hydrogen either publishes an equivalent Shop Pay impression event from the local button, or public consumer/API docs explicitly document that the local button does not emit shop-js impression analytics.

## Shop Pay button checkout params are limited

**Status:** Open
**Added:** 2026-05-29

**What:** The local Shop Pay button constructs checkout URLs with the supported params: `payment`, `source`, `source_token`, and `channel`. It does not expose an API for callers to pass arbitrary additional search params. In headless, checkout URLs often need tracking/session query params so checkout can keep the buyer tied to the same storefront analytics session.

**Current workaround:** Hydrogen points the button at same-origin checkout routes. In production, `/checkout` redirects to the current Storefront API cart checkout URL, while `/cart/{variant}:{quantity}` redirects to the Shopify store-domain cart permalink. When a cart exists, the cart permalink interceptor also merges search params from the current cart checkout URL so tracking/session params are preserved before adding the Shop Pay params generated by the local button.

**Why it matters:** Hydrogen still routes Shop Pay traffic through checkout interceptors to preserve headless tracking/session params that the button cannot accept directly.

**Done when:** The Shop Pay button supports caller-provided search params or Hydrogen exposes a clear extension point for preserving needed tracking/session params when building both checkout and variant cart URLs.

## Hydrogen error logging policy

**Status:** Resolved (2026-07-28)
**Added:** 2026-05-25

**What:** Runtime helpers previously logged errors ad hoc. There was no package-level policy for when to log, throw, expose reactive error state, or invoke a user-supplied reporter.

**Why it matters:** Silent runtime failures are difficult to debug, but unstructured console logging can be noisy and inconsistent across framework adapters.

**Done when:** Hydrogen has a documented error reporting contract for browser runtime failures, including adapter behavior, optional user hooks, and test expectations.

**Resolution:** The logging contract is implemented in `src/core/logging/` and documented in the repo-level `error-reporting` skill (`skills/error-reporting/SKILL.md`). Runtime helpers obtain a scoped logger via `getLogger(scope)`; callers configure the global sink and level through `configureLogging({ logger, level })`. The `no-console` lint rule enforces that the sanctioned `console` call sites are the built-in sink in `src/core/logging/logging.ts` and the serialized consent bootstrap in `src/core/shopify-scripts/consent-script.ts`. Serialized inline-script import chains (analytics bus/destination-manager, consent bootstrap) are documented exceptions — they always write to `console` with the standard `[hydrogen:<level>:<scope>]` prefix.

## No cross-entrypoint import boundary enforcement

**Status:** Open
**Added:** 2026-05-05

**What:** There is no automated check preventing framework adapter entrypoints from importing runtime code that should stay out of those adapter bundles. Entrypoints are meant to be independently tree-shakeable, but nothing enforces this today.

**Why it matters:** A single cross-entrypoint import silently couples entrypoints at build time — consumers who only import a framework adapter could end up pulling in unrelated code, breaking tree-shaking guarantees.

**Ideal solution:** `eslint-plugin-import`'s `no-restricted-paths` rule, which enforces path-based boundaries at lint time (editor feedback). However, oxlint — our target linter — [does not yet support this rule](https://github.com/oxc-project/oxc/issues/13789).

**Acceptable interim solutions (pick one):**
1. A post-build boundary check script (~30 lines) that walks each entrypoint's built output and asserts no imports cross boundaries. Runs in CI.
2. Run ESLint alongside oxlint for this single rule, using `eslint-plugin-oxlint` to disable overlap.

**Done when:** A CI check fails if an adapter entrypoint imports code outside its intended dependency boundary.

## Per-query GraphQL API version override

**Status:** Closed — documented workaround (2026-07-28)
**Added:** 2026-05-07

**What:** The Storefront API version is currently set once at client creation time (`STOREFRONT_API_VERSION`). There is no mechanism to override the version for an individual query.

**Use case:** Developers sometimes need to hit `unstable` or a newer API version for specific queries before doing a full migration. frandiox raised this as a known Hydrogen use case.

**Why it's deferred:** Overriding the version per-query is a type-safety footgun — `apiVersion` only changes endpoint routing, while Hydrogen's bundled `gql.tada` schema still controls type inference. A query running against a different version could have types that don't match the actual response shape, with no compiler warning.

**Possible approaches:**
1. A `dangerously_overrideVersion` parameter on `graphql()` — makes the risk explicit in the API name.
2. Instruct users to create a separate `createStorefrontClient({ config: { apiVersion } })` instance for unstable queries, keeping version routing explicit.

**Done when:** We decide on an approach and either implement the escape hatch or document the separate-client workaround.

**Resolution:** Approach #2 was chosen: create a separate `createStorefrontClient` instance with a different `apiVersion` for queries that need a different Storefront API version (e.g. `unstable`). This is already supported via the client config and keeps version routing explicit. The escape-hatch parameter (approach #1) was rejected as a type-safety footgun: a query running against a different version would have types that don't match the actual response shape, with no compiler warning. Hydrogen's bundled `gql.tada` schema still controls type inference, so queries against fields outside that schema need their own typing. The workaround is documented in the JSDoc on the `apiVersion` field of `CommonOptions` in `src/client/types.ts`.
