# Cart traps

Read before migrating the cart drawer, `/cart` page, or add-to-cart flow. These all present as "add to cart does nothing / cart is empty" while the mutation is actually fine — the render source or gating is wrong.

- **Cart lives at `/api/cart`; open the drawer off the cart store, not a fetcher.** `createCartServerHandlers()` owns `GET`/`POST /api/cart` with an `intent` field (`add`, …). But the client uses the library `useCartForm()` — `formProps()` submits through the library's own cart store (`store.handleFormSubmit` with `preventDefault`), so React Router's `useFetchers()` never sees the request. Any classic-Hydrogen "open the drawer when a `/api/cart` fetcher is in flight" logic silently stops firing: the mutation succeeds but the drawer never opens. Drive the drawer from the store via `useCart(...)` instead. And do **not** key off absolute `data.totalQuantity` — it jumps `0 → N` when an existing cart hydrates, so the drawer pops open on every page load. Watch a **mutation** signal: `useCart((s) => s.pending.lines.size > 0)` transitioning to true is the "an add is in flight" edge that fires only on user action (initial load leaves `pending` empty). The cart mutation and the drawer-open UI are separate concerns; verify both.
- **Render every cart surface from the store, not deferred loader data.** A classic-Hydrogen layout resolves the cart in the root loader and threads it into the drawer (and `/cart` page) through `<Suspense><Await resolve={cart}>`. In the preview library the cart is a client store, and the root loader usually no longer returns a `cart` field at all — so a carried-over `<Await resolve={cart}>` resolves to `undefined` and the drawer/page renders permanently empty *even though adds succeed and the header count updates* (the header reads the store; the drawer reads the dead promise). This looks like "add to cart does nothing" but the mutation is fine — only the render source is wrong. Point every cart surface at `useCart((s) => s.data)` and delete the deferred `cart` loader plumbing.
- **Gate line-item controls on optimistic identity, not `pending`.** The store already applies quantity edits optimistically and uses `pending.lines` only to reconcile/roll back. A scaffold that disables +/−/remove while `pending.lines.has(lineId)` locks the buttons for the entire `/api/cart` round-trip on every click — a visible "buffer" the classic optimistic cart never had. Disable only genuinely-new lines with no real cart-line id yet (their id carries the store's optimistic prefix, `optimistic:`); leave in-flight edits on real lines enabled so successive clicks stay instant.
- **Seed `CartProvider` `initialData` on the server or the cart flickers on first paint.** With no `initialData` the store starts empty and fetches `/api/cart` after hydration, so the cart page and drawer render their empty-state text first, then pop to the real cart. Fetch the cart in the root loader (`cartHandlers.get({storefrontClient, request})`) and pass the **full handler envelope** — `{cart, errors?}`, not `data.cart` — to `<CartProvider initialData={…}>`. **Await** it in the loader: a deferred promise leaves SSR empty and the flicker remains. Semantics: `{cart: null}` renders empty with no client retry, `undefined` triggers the post-hydration fetch.
