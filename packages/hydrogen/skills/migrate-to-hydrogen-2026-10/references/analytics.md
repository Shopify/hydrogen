# Analytics traps

Read before migrating analytics + consent. Migrate the two together and after localization (so the i18n/currency inputs are settled before you wire the `shop` payload).

- **Port the analytics events — the bus still exists, only the classic React sugar is gone. Do not drop events.** Classic Hydrogen split analytics three ways: `Analytics.Provider` auto-published `page_viewed` + the cart events by diffing the `cart` prop; `<Analytics.ProductView/SearchView/CollectionView>` published the route events; and the app's own component only *subscribed* and pushed to `dataLayer`. The 2026-10 library removes all of that (`Analytics.Provider`, the `<Analytics.*View>` components, `useAnalytics`, `getShopAnalytics` — and there is no `createStorefrontAnalytics` either). The current wiring: render `<ShopifyScripts>` (from `@shopify/hydrogen/react`) in the root head with `i18n`, `shop`, `consent`, `navigate`, and `routes` (your route templates) — it creates the bus and exposes it as the client-only singleton `window.Shopify.analytics`. Everything else is app code that talks to that singleton: publish route events (`AnalyticsEvent.PAGE_VIEWED`/`PRODUCT_VIEWED`/`COLLECTION_VIEWED`/`SEARCH_VIEWED`/`CART_VIEWED`) from tracker components on location change, and wire cart deltas with `useCartAnalytics()` (React) or `trackCartAnalytics(cartStore)` — never by hand-diffing the cart. The trap is that the easy migration deletes the classic `subscribe` calls and rewrites the tracking component to publish only page views off `useLocation` — the commerce funnel (`view_item`/`view_cart`/`add_to_cart`/`remove_from_cart`) silently disappears while the build stays green. **Follow the `hydrogen-analytics` packaged skill (`node_modules/@shopify/hydrogen/skills/hydrogen-analytics`) for the reference wiring** — it is exactly this port.
- **The bus needs the same-origin SFAPI proxy from `handleShopifyRoutes`.** Analytics posts through the app's own origin (wired by the `hydrogen-request-handlers` setup the outline already installs). Without it, the bus falls back to deprecated cookie-based tracking and checkout session continuity breaks — no build error, just degraded attribution.
- **Cart and client-only rules.** `useCartAnalytics()`/`trackCartAnalytics` run client-side only (they throw when `window.Shopify.analytics` is missing, i.e. during SSR — keep them in a client effect). Optimistic placeholder lines (see `references/cart.md`) lack the product fields Shopify analytics requires, so the template's `toAnalyticsCart` returns `null` for a cart without `id`/`updatedAt` and drops lines whose merchandise or product details are missing rather than publishing malformed events. Keep that filtering when you port it.
- **`shop` payload and channel.** Build the `shop` payload in the root loader yourself (`getShopAnalytics` is gone). Its shape is `{shopId, storefrontId, myshopifyDomain}` — `shopId` is the Shop GID from a Storefront API `shop { id }` query (the template reads it in the root loader; the numeric `SHOP_ID` env var is for Customer Accounts, not this payload), and `storefrontId` comes from `PUBLIC_STOREFRONT_ID` (the template passes `""` for mock stores and switches to `channel: 'headless'`). The `channel` defaults to `"hydrogen"`, which requires a real `storefrontId`; a headless/custom channel passes `channel: 'headless'`. Use the `analytics` prop only for optional bus config such as `customData`; do not push market country/language through the consent config. `ShopifyScripts` also accepts opt-in extras (`account`, `inbox`, `webMcp`, `shopifyAnalytics`, `debug.standardEventsInspector`, `nonce`) — read the installed `ShopifyScriptsOptions` type before wiring them.
- **Consent gates destinations, not subscribers.** Shopify Customer Privacy decides what reaches **destinations**: raw `subscribe` callbacks observe events pre-consent, while destinations receive a consent-allowed replay only. A store that had its own destination (e.g. GTM → `dataLayer`) keeps that mapping verbatim and registers it via `addDestination({name, setup: ({subscribe}) => …})` on the bus; `setup` only subscribes and maps — load the GTM script tag elsewhere, since the bus forbids loading third-party scripts or setting cookies inside `setup`. Nothing auto-publishes the route events — a bus with destinations but no `publish` calls tracks nothing.
