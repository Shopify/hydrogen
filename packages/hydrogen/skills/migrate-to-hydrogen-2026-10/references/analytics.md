# Analytics traps

Read before migrating analytics + consent. Migrate the two together and after localization (so the i18n/currency inputs are settled before you wire the `shop` payload).

- **Port the analytics events — the bus still exists, only the classic React sugar is gone. Do not drop events.** Classic Hydrogen split analytics across `Analytics.Provider` (auto-published `page_viewed` + the cart events by diffing the `cart` prop), `<Analytics.ProductView/SearchView/CollectionView>` (published the route events), and, where the store had GTM or `dataLayer` glue, an app component that only *subscribed*. The 2026-10 library removes all of that (`Analytics.Provider`, the `<Analytics.*View>` components, `useAnalytics`, `getShopAnalytics` — and there is no `createStorefrontAnalytics` either). The current wiring: render `<ShopifyScripts>` (from `@shopify/hydrogen/react`) in the root head with `i18n`, `shop`, `consent`, `navigate`, and `routes` (your route templates) — it creates the bus and exposes it as the client-only singleton `window.Shopify.analytics`. Everything else is app code that talks to that singleton: publish route events (`AnalyticsEvent.PAGE_VIEWED`/`PRODUCT_VIEWED`/`COLLECTION_VIEWED`/`SEARCH_VIEWED`/`CART_VIEWED`) from tracker components on location change, and wire cart deltas with `useCartAnalytics()` (React) or `trackCartAnalytics(cartStore)` — never by hand-diffing the cart. The trap is that the easy migration deletes the classic `subscribe` calls and rewrites the tracking component to publish only page views off `useLocation` — the commerce funnel (`view_item`/`view_cart`/`add_to_cart`/`remove_from_cart`) silently disappears while the build stays green. **Follow the `hydrogen-analytics` packaged skill (`node_modules/@shopify/hydrogen/skills/hydrogen-analytics`) for the reference wiring** — it is exactly this port.
- **The bus needs the same-origin SFAPI proxy from `handleShopifyRoutes`.** Analytics posts through the app's own origin (wired by the `hydrogen-request-handlers` setup the outline already installs). Without it, the bus falls back to deprecated cookie-based tracking and checkout session continuity breaks — no build error, just degraded attribution.
- **Cart and client-only rules.** Cart tracking is client-only. `trackCartAnalytics(store)` throws when `window.Shopify.analytics` is missing, which includes SSR, so call it from a client-only effect. `useCartAnalytics()` already wraps that effect, so call the hook once from a component rendered inside `CartProvider` (the template's `CartAnalyticsTracker`) and never from inside another effect. Optimistic placeholder lines (see `references/cart.md`) lack the product fields Shopify analytics requires, so the template's `toAnalyticsCart` returns `null` for a cart without `id`/`updatedAt` and drops lines whose merchandise or product details are missing rather than publishing malformed events. Keep that filtering when you port it.
- **`shop` prop, channel, and `shopifyAnalytics`.** Build the `ShopifyScripts` `shop` prop yourself in the root loader (`getShopAnalytics` is gone). Its type is `ShopifyScriptsShop`: `{shopId, storefrontId, myshopifyDomain}`. `shopId` takes either the numeric `SHOP_ID` env var or the Shop GID from a Storefront API `shop { id }` query, and the bus normalizes both to a GID. The template queries it, so mock.shop works without env. `storefrontId` comes from `PUBLIC_STOREFRONT_ID`. Pass `""` when there is none (it also keeps PerfKit off), not the `"0"` the packaged `hydrogen-analytics` skill shows. The per-event `shop` payload (`ShopAnalytics`) is derived from that prop plus `channel`. `channel` defaults to `"hydrogen"`, which needs a real `storefrontId`. Without one, pass `channel: 'headless'`. `channel` and the optional `customData` go on the `analytics` prop. Do not push market country/language through the consent config. `shopifyAnalytics` and `webMcp` default to `true`, so a store without a `storefrontId` must pass `shopifyAnalytics={false}` or Shopify's analytics script loads with nothing to attribute to. The template's `resolveShopIdentity` (`app/lib/shop.ts`) derives all of this from env. Reduced to one block, the root renders:

  ```tsx
  const storefrontId = env.PUBLIC_STOREFRONT_ID ?? "";
  <ShopifyScripts
    i18n={{ country, language, currency }}
    shop={{ shopId, storefrontId, myshopifyDomain }}
    analytics={{ channel: storefrontId ? "hydrogen" : "headless" }}
    shopifyAnalytics={storefrontId !== ""}
    consent={{ mode: "default-banner" }}
    navigate={navigate}
    routes={routeTemplates}
  />
  ```

  The remaining props (`account`, `inbox`, `debug.standardEventsInspector`, `nonce`) are opt-in. Read the installed `ShopifyScriptsOptions` type before wiring them.
- **Every consumer is a destination, and consent gates delivery.** The bus is `publish`, `addDestination`, and `getConfig`. It has no `subscribe`, so there is no ungated observer. `publish` buffers up to 500 events. Destinations receive events live once Customer Privacy allows analytics, plus a replay of the buffer, and the bus clears the buffer if consent completes as denied. A store that had its own destination (GTM writing to `dataLayer`, say) keeps that mapping verbatim and registers it via `addDestination({name, setup: ({subscribe}) => …})`. `setup` only subscribes and maps. Load the GTM script tag elsewhere, because the `setup` contract says not to load third-party scripts or set cookies there. Nothing auto-publishes bus events. `initializeShopifyScripts` documents that it "sends a page view event", but that is the Standard Events DOM event for Shopify's own scripts, not a bus `page_viewed`. A bus with destinations but no `publish` calls tracks nothing.
